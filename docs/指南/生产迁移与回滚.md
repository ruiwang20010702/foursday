# 生产迁移与回滚

> 适用版本：`v0.8.0-rc.1`。这是生产操作手册，不是安装成功证明。GitHub Release 不会自动部署或激活生产。

## 1. 迁移结论

`0.6.x → 0.8` 不是原地升级，也不提供旧Runtime兼容层：

- 旧版自研 Runtime、任务/计划/审批表、管理台、常驻服务和迁移历史不再属于新架构；
- `db/schema.sql` 只创建新架构的记忆候选表；
- 新 schema 禁止覆盖旧生产数据库；
- 新版本使用独立 Profile、最小配置和数据库；旧业务表不迁入新架构；
- 切换失败时停止新Gateway、恢复`shadow/send=false`并前滚修复，不重新启用旧Runtime；
- 旧目录只可在迁移窗口短期归档以便取证，确认新入口可用后应退出运行环境；PostgreSQL、钥匙串和gbrain数据必须单独处置。

## 2. 角色与权限

| 角色 | 责任 |
|---|---|
| 发布负责人 | 确认目标 SHA、备份、Shadow、acceptance、激活和回滚决定 |
| 数据库负责人 | 创建新库、应用新 schema、验证备份；不把连接串写入日志 |
| Foursday | 生成安装/状态/验收计划，执行已明确授权的本机步骤 |
| Codex 工作循环 | 不具备生产部署、数据库写入、服务控制和 Release 权限 |

生产写入、Keychain 变更、服务切换和真实发送必须在独立任务中明确授权。

## 3. 目标拓扑

```text
旧版本（退出运行）
├── 旧 Release / Profile：停止，可短期归档取证
├── 旧生产配置：不导入新Profile
├── 旧数据库：按独立数据保留策略处理
└── 旧服务：卸载，不作为回滚目标

新版本（v0.8）
├── 精确 GitHub Release SHA
├── 新 Foursday Profile
├── 新 FOURSDAY_* 私有配置
├── 新 PostgreSQL 记忆候选库
└── 新 Gateway（先 Shadow，后独立激活）

共享但不复制
└── 个人 gbrain：专用只读 OAuth + 可选独立写入 checkout
```

## 4. 发布前门禁

### 4.1 代码与远端

- [ ] GitHub Release 为非 Draft 的 Pre-release；
- [ ] 标签指向完整 `main` SHA；
- [ ] Node 22、Node 24、安全扫描在同一 SHA 成功；
- [ ] 本机源码与目标 SHA 一致，工作树无未审阅改动；
- [ ] `npm run check:full`、`check:python`、`reuse:verify` 和 audit 通过；
- [ ] 候选文件无真实秘密、运行快照和本机私人路径。

### 4.2 当前生产

- [ ] 记录旧 Release SHA、Profile 版本、服务标签和运行状态；
- [ ] 确认自动发送、主动工作、计划执行和记忆写入当前开关；
- [ ] 确认没有执行中外部副作用；
- [ ] 确认单写者：同一钉钉账号最多一个发送 Gateway；
- [ ] 如需取证，导出旧 Profile 私有归档；不得把它作为可重新激活的兼容运行时；
- [ ] 数据库做可恢复备份并独立验证可读性；
- [ ] 记录 Keychain 引用名称，不输出值。

### 4.3 新环境

- [ ] 新数据库与旧库物理隔离；
- [ ] 新配置来自 `deploy/foursday.example.json`，权限 `600`；
- [ ] 私有源配置只包含当前`FOURSDAY_*`字段；Profile内`production.json`精确投影当前白名单，不能出现旧`DATABASE_URL`或`AI_EMPLOYEE_*`字段；
- [ ] `.env`中的`FOURSDAY_RELEASE_SHA`与`foursday-release.json`精确一致；fresh Shadow ledger事件均带同一SHA，旧事件不参与验收；
- [ ] 项目注册表来自 `distribution/projects.example.json`，目录均规范存在；
- [ ] DWS 与 Codex 使用绝对可执行路径；启用Stream主唤醒时DWS必须为`v1.0.59+`；
- [ ] gbrain 读取客户端是专用只读 OAuth；
- [ ] 写入 gbrain 时使用专用 checkout，默认先保持关闭。

任一门禁失败：NO-GO，不进入服务安装。

### 4.4 DWS Stream升级门禁

生产DWS低于`v1.0.59`时，不得在Gateway运行期间原地升级。必须：

1. 记录当前版本、登录状态和可回滚备份，不输出token；
2. 先执行`dws upgrade --dry-run`；
3. 停止Gateway并保持发送关闭，再执行带SHA256校验的DWS升级；
4. 回读`dws auth status`，随后用`dws event +listen-im --kind all-direct --events message --dry-run`验证事件计划；
5. 认证出现`ciphertext_key_mismatch`时立即停止，不执行`auth reset`、不覆盖凭据；按DWS指引完成可读旧凭据的迁移或回滚旧二进制；
6. 只有认证、事件ready、文件降级和30秒兜底均通过后，才进入Foursday Shadow。

复制到其他路径的隔离DWS可能因Keychain/DEK绑定无法读取生产登录态；这只能证明命令和二进制能力，不能替代目标路径上的认证迁移验收。

## 5. 安装与配置

### 5.1 预览

```bash
npx --no-install foursday install

FOURSDAY_CONFIG_FILE=/absolute/private/foursday.json \
  npx --no-install foursday configure \
  --registry /absolute/private/projects.json
```

预览必须显示：零发送、零生产写入、Gateway 不启动。

### 5.2 应用安装

```bash
npx --no-install foursday install --apply

FOURSDAY_CONFIG_FILE=/absolute/private/foursday.json \
  npx --no-install foursday configure --apply \
  --registry /absolute/private/projects.json
```

配置完成后回读：

- Foursday Profile 与锁定上游版本；
- 组件只有 DWS、项目路由、个人记忆桥、Codex Proxy/MCP、Session/Gateway 和 project-work Skill；
- `mode=shadow`、`send=false`；
- 配置和状态文件权限；
- 旧 Runtime 未被自动启动。

同时回读消息入口：

- `eventWake.enabled=true`且新版DWS出现ready；旧版或建联失败必须明确显示降级，不能伪装成功；
- 文件事件仍保留；`FOURSDAY_DINGTALK_FALLBACK_MS`默认30000；
- 历史检查点保留120秒投影保护窗，Gateway启动按10分钟窗口回放未去重消息；
- 同一Sidecar的DWS CLI命令必须串行，三人以上白名单启动时不得出现本地数据锁竞争；
- 启动回放必须在Gateway登记适配器后释放；回放消息既有入站证据又必须出现对应Agent Turn，不能只增加去重检查点；
- 出站基础稳定窗口8000毫秒、最大20000毫秒；
- 钉钉当前运行状态问题优先使用连接器注入的实时Profile快照，其他入口调用`foursday_runtime_status`；均不得从gbrain或旧Session作答；
- Runtime MCP五个工具必须带完整权限注解，Profile必须回读`startup_timeout_sec=5`与`tool_timeout_sec=10`；缺失任一项不得进入Active；
- 用同一Profile分别覆盖普通联系人`list-by-sender`、本人自聊`list-direct`和群聊`search-advanced`的fileId文件消息：原子结果可只有展示文本，但`+messages-mget`必须回读完整结构化`resourceRefs`；下载命令必须按`fileId`类型执行，禁止硬编码`mediaId`；
- 文件消息与随后文本必须在3秒安静窗/8秒总窗内形成一个Turn，工作上下文附件数量大于0；`foursday_list_attachments`、`foursday_stage_attachment`和项目读取后的字节摘要必须一致；
- 任一详情富化/下载失败时检查点不得消费该消息；重试成功后只产生一个Turn。验收结束必须清理私有缓存和`.foursday-inbox`测试文件；
- Markdown变换后的唯一回读、自消息过滤和`sendBlocked`自动停发测试通过；
- 配置不会因为升级自动扩大联系人、群聊或发送权限。

### 5.3 Codex 独立登录与验证

```bash
FOURSDAY_CONFIG_FILE=/absolute/private/foursday.json \
  npx --no-install foursday login --apply

FOURSDAY_CONFIG_FILE=/absolute/private/foursday.json \
  npx --no-install foursday verify --apply
```

验证必须证明：独立 CODEX_HOME、工具证据、随机事实回读、工作区摘要不变、零发送、零生产写、零部署。

Runtime MCP还必须运行真实App Server门禁：

```bash
npm run runtime:verify-mcp -- --iterations=20
```

通过标准：状态、附件列举、项目记忆读取和附件暂存各20次，合计80次成功、失败0、各工具P95小于2秒；记忆候选只在隔离数据库测试。命令结束后不得存在App Server/MCP残留进程、临时Codex信任目录、消息发送、gbrain写入、计划执行或生产部署。

附件灰度还必须使用无敏感TXT执行一次真实零发送Shadow：DWS详情返回`resourceRefs[].type=fileId`，下载字节与MCP暂存字节SHA-256一致，Codex同时出现附件列举、附件暂存和文件读取工具证据并生成自然摘要；不允许把“请重新上传”作为通过结果。

## 6. 新数据库

1. 创建独立空库与最小权限账号。
2. 通过独立数据库运维流程应用 `db/schema.sql`。
3. 回读仅存在 `foursday_memory_candidates`、`foursday_memory_candidate_sources` 及其索引。
4. 验证加密候选写入/读取和租约测试。
5. 保持 `FOURSDAY_GBRAIN_WRITE_ENABLED=false`，直到个人 gbrain 写入回读单独验收。

禁止：

- 对旧生产库执行 `db/schema.sql`；
- 删除旧迁移表来“模拟新安装”；
- 把旧任务、草稿、审批、计划和发送记录复制到新候选表；
- 在日志、命令历史或 PR 中出现数据库 URL/密码。

## 7. Shadow 服务

### 7.1 安装并启动

```bash
npx --no-install foursday gateway install-shadow --apply
npx --no-install foursday gateway start-shadow --apply
npx --no-install foursday status
```

Shadow 可以监听、路由、读取记忆、调用 Codex 和记录证据，但真实发送必须被 DWS Bridge 拒绝。

### 7.2 Shadow 必验场景

1. allowlist 私聊进入；
2. 陌生私聊拒绝；
3. 白名单群 `@` 进入、未 `@` 拒绝；
4. 项目唯一命中和会话追问；
5. gbrain 精确页面读取与不可用降级；
6. 项目事实核对；
7. 文档/分析；
8. 代码修改、测试和回读（隔离试验项目）；
9. 高风险命令、路径和秘密拒绝；
10. 人工接管；
11. 重启后不漏不重；
12. send-disabled 与零重复证据。
13. 5—8秒间隔的三条碎片只产生一个最终回复，旧generation未进入发送账本；
14. 分段延迟证据包含消息发现、合并、Agent、发送和回读阶段；

### 7.3 验收回执

使用有界 shadow ledger、重启证据和代码证据生成 acceptance。回执必须：

- 私有普通文件；
- 绑定完整目标 SHA；
- 不含消息正文和身份；
- 未过期；
- 十类场景均为 true；
- 证据摘要可重新计算。

## 8. 激活

### 8.1 激活前复核

- 旧发送者已停止且 disabled；
- 新 Gateway Shadow 健康；
- acceptance 绑定当前 Profile 与目标 SHA；
- 新数据库和 gbrain 读链健康；
- DWS 发送目标、当前账号和回读能力验证；
- 已准备立即停止命令和新Profile的前滚修复步骤。

### 8.2 预览与应用

先运行不带 `--apply` 的激活预览，记录派生确认值；确认目标、SHA 和 receipt 不变后，再在独立授权任务执行 apply。

激活后必须回读：

- `mode=active`；
- `sendEnabled=true`；
- Gateway running、service enabled、checkpoint healthy、mode consistent、ready；
- 旧写入者未运行；
- 一条仅发给本人测试会话的真实回执（需要单独发送授权）。

## 9. 失败分级

| 阶段 | 失败 | 处置 |
|---|---|---|
| 安装前 | 测试、密钥扫描、备份失败 | 停止；生产不变 |
| 安装/Profile | installer、摘要、doctor、依赖裁剪失败 | 自动恢复更新前的新架构Profile/依赖；Gateway 不启动 |
| 配置 | 未知字段、内联秘密、路径不安全 | 修配置；禁止降级校验 |
| Codex verify | 登录、审批、工具证据或摘要失败 | 保持 Shadow/停止；不激活 |
| 数据库 | schema、加密、租约失败 | 新库废弃或修复；旧库不动 |
| Shadow | 路由、记忆、接管、重启、DLP失败 | 修复并重新积累完整 acceptance |
| 激活 | 单写者、SHA、回执、启动失败 | 恢复 Shadow/send=false，停止新服务 |
| 发送未知 | 没有唯一 message ID/readback | 停止发送，人工核对，不重试 |

## 10. 回滚

### 10.1 激活前

候选失败时：停止新 Shadow Profile，保留日志和私有证据，修复候选后重新验证。旧Runtime保持退出，不作为兼容回退目标；旧数据库和数据保留策略不应被候选顺带修改。

### 10.2 激活后可捕获失败

1. 将新 Profile 恢复为 `shadow/send=false`；
2. 停止并禁用新 Gateway；
3. 回读新 Gateway 未运行；
4. 保留新数据库，不做反向迁移；
5. 从最后一个可验证的新架构提交前滚修复并重新完成Shadow验收；
6. 再次确认只有一个发送者；
7. 若需要真实发送验证，另行授权本人自聊测试。

### 10.3 不可自动回滚

- 已经发出的钉钉消息；
- 已发生的外部系统副作用；
- 已推送到个人 gbrain Git 的新提交；
- 生产数据库中已对外消费的数据。

这些情况只做补偿、退役或人工纠正，不能宣称“自动撤销”。

## 11. 发布后观察

### 11.1 首日

- 持续观察事件ready/降级、消息发现P50/P95、Agent P50/P95、检查点、DWS 错误、发送 unknown、身份拒绝、接管和 Gateway 重启；
- 只对本人自聊和已知测试联系人逐步放量；
- 出现重复、越权、秘密、跨项目或接管失败立即停止。

### 11.2 首周

- 评审路由准确率、证据完整率、任务闭环率和用户确认时间返还；
- 抽查记忆候选与 gbrain 晋升；
- 统计不是固定业务指标问题的连续追问表现；
- 未完成长期业务验收前保持 Pre-release。

### 11.3 个人 gbrain 与真实发送灰度

进入真实发送前必须同时满足：`readEnabled=true`、`writeEnabled=false`、两个注册项目页可由专用OAuth精确读取、对应上下文进入真实Codex回合、promoter在`--quiet-idle`下退出码为0、计划仍为paused。旧错误记录可以保留，但不能把历史error误报为当前仍失败。

| 阶段 | 范围 | 最小样本 | 放行条件 | 立即停止条件 |
|---|---|---:|---|---|
| Shadow | 本人、谷鸿基、周行健，仅生成候选 | 2个项目各1次 | 精确来源、工作区不变、零发送、零写入 | 记忆越权、来源缺失、配置泄密 |
| 本人灰度 | 仅本人自聊真实发送 | 5个不同任务 | 重复0、内部状态文本0、未知回执0、接管有效 | 任一误发、重复、秘密、跨项目 |
| 可信联系人灰度 | 谷鸿基、周行健私聊 | 合计10个真实请求 | 项目路由正确、追问连续、P95消息发现≤30秒、P95端到端≤150秒 | 任一越权；连续2次超时；负责人已回复后仍发送 |

灰度期间群聊、主动工作、计划执行和gbrain写入继续关闭。只有精确提交完成提交、推送、Profile更新、fresh Shadow ledger、重启证据和代码证据后，才生成同SHA acceptance；旧提交回执不得复用。

## 12. 当前版本边界

`v0.8.0-rc.1` 的源码、Release、技术部署和生产激活必须分别回读。GitHub Release 本身不证明某台主机已经部署或启用；生产状态只能由目标主机上的Profile、服务、检查点、数据库和真实回读共同证明。
